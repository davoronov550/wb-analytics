## 7.1. Ветка и рабочие соглашения

### Ветка

```
main                          ← продакшн, продолжает получать фиксы
  └── migration/fastapi-microservices   ← длинная ветка миграции (создана от 00aa21c)
        ├── mig/T0xx-…        ← короткие ветки под задачу, вливаются обратно
        └── …
```

`migration/fastapi-microservices` живёт до конца фазы 5 и вливается в `main`
после того, как Django выведен из контура. `main` в неё вливается регулярно
(не реже раза в неделю), чтобы не копить конфликты.

Ветка задачи создаётся от `migration/…`, называется `mig/T0xx-краткое-имя`,
вливается `--no-ff`, чтобы история задач читалась.

### Коммиты

Формат репозитория сохраняется: `<type>: <описание>` на русском.
Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`.
Атрибуция отключена глобально.

### Определение готовности задачи

Задача закрыта, когда выполнено всё:

1. Код написан, `ruff` и `mypy --strict` проходят.
2. Тесты написаны **до** реализации там, где это применимо; покрытие модуля
   не ниже 80 %.
3. CI зелёный целиком, а не «упало не по моей вине».
4. Если задача трогает контракт — `contracts/` обновлены, `schemathesis` или
   `buf breaking` проходят.
5. Если задача трогает решение из документов 1-6 — документ обновлён в том же
   коммите.

### Что не делаем

- Не рефакторим `domain/` и `application/` «заодно». Единственное
  санкционированное исключение — `Ordering` (см. §7.6).
- Не удаляем Django-код до фазы 5, даже когда сервис его заменил.
- Не оптимизируем то, что не измерено нагрузочным тестом.

## 7.3. `libs/platform` — спецификация модулей

Ядро, от которого зависят все девять сервисов. Пишется первым, потому что
шаблон сервиса опирается на него.

| Модуль | Содержимое | Ключевые решения |
|---|---|---|
| `config.py` | База на Pydantic Settings, `.env` + переменные окружения | Валидация при старте, падать на неполной конфигурации, а не в рантайме |
| `logging.py` | `structlog` → JSON | Контекстные поля `trace_id`, `service`, `owner_id` привязываются через contextvars, а не передаются аргументами |
| `otel.py` | Бутстрап трассировки и метрик | Инъекция/извлечение `traceparent` для **Kafka-заголовков и gRPC-metadata** — единственное место, где это реализовано |
| `errors.py` | Иерархия ошибок + конверт | Одно отображение `DomainError → HTTP-код` и `→ google.rpc.Status`; текст наружу не раскрывает внутренности |
| `pagination.py` | Keyset-курсор | Самый нетривиальный модуль, см. §7.5 |
| `db.py` | Async-engine, сессия, healthcheck | `statement_cache_size=0` зашит — забыть его нельзя (риск R8) |
| `outbox.py` | Таблица, запись в транзакции, relay | Relay — переиспользуемый воркер, а не копипаста по сервисам |
| `idempotency.py` | `Idempotency-Key` в Redis | Хранит ключ + хеш тела + готовый ответ, TTL 24 ч |
| `kafka.py` | Продюсер, консьюмер, дедуп | Дедуп по `event_id`; ручной коммит офсета **после** обработки, не до |
| `grpc_.py` | Серверные и клиентские интерцепторы | Трассировка, логи, отображение ошибок, health-протокол |
| `auth.py` | Проверка JWT, JWKS-клиент | Кеш ключей с фоновым обновлением; отзыв — проверка в Redis только для refresh |
| `health.py` | `/healthz`, `/readyz` | `readyz` проверяет зависимости, `healthz` — только процесс |
| `testing/` | Фикстуры testcontainers | PostgreSQL, ClickHouse, Kafka (KRaft), Redis — по одному контейнеру на сессию pytest |

**Правило.** Если код появляется во втором сервисе копипастой — он принадлежит
`libs/platform`. Это единственная защита от дублирования на девяти сервисах
(митигация риска R5).

Критический путь — `libs/platform` → шаблон сервиса. Всё остальное можно вести

**Почему контракт снимается после `libs/platform`, а не первым.** Работа с
`drf-spectacular` идёт в `backend/` и ни от чего не зависит; но если начать с
неё, `libs/platform` окажется на критическом пути фазы 1. Порядок выбран так,
чтобы фаза 1 не ждала.

## 7.5. Ключевое техническое решение: keyset при многоуровневой сортировке

Самое сложное место фазы 1, и его нужно решить до написания кода.

### Проблема

Приём «сравнение кортежей» работает только когда **все** уровни сортировки
идут в одну сторону:

```sql
WHERE (reviews_count, external_id) < ($1, $2)     -- обе DESC, корректно
```

Пресеты интерфейса содержат смешанные направления — например
«Дешевле ↑ + рейтинг ↓». Для них кортежное сравнение даёт неверный результат:
строки на границе страниц теряются или дублируются.

### Решение — развёрнутая цепочка условий

Для ключей `(f1 DESC, f2 ASC, external_id DESC)` и курсора `(v1, v2, vid)`:

```sql
WHERE  (f1 <  $1)
   OR  (f1 =  $1 AND f2 >  $2)
   OR  (f1 =  $1 AND f2 =  $2 AND external_id < $3)
ORDER BY f1 DESC, f2 ASC, external_id DESC
LIMIT  $n + 1
```

Генерируется из списка ключей сортировки в `libs/platform/pagination.py`.
Последний уровень — всегда `external_id`, иначе строки с одинаковыми
значениями ведут себя недетерминированно.

### Индексы: почему нельзя проиндексировать всё

Пять сортируемых полей в произвольном порядке и с произвольным направлением
дают сотни комбинаций. Индексировать их все невозможно.

**Решение:** индексируются пресеты интерфейса и одиночные сортировки —
покрывают практически весь реальный трафик:

```sql
CREATE INDEX ON product (reviews_count DESC, external_id DESC);              -- по умолчанию и пресет 1
CREATE INDEX ON product (rating DESC, reviews_count DESC, external_id DESC); -- пресет 2
CREATE INDEX ON product (sale_price ASC, rating DESC, external_id DESC);     -- пресет 3
CREATE INDEX ON product (price, external_id DESC);
CREATE INDEX ON product (name, external_id DESC);                            -- см. оговорку ниже
```

Произвольная комбинация вне этого списка обслуживается, но медленнее — и
логируется с меткой `unindexed_sort`, чтобы решение о новом индексе принималось
по данным, а не по догадке.

### Оговорка про сортировку по названию

`name` — текст; порядок зависит от collation. Индекс обязан быть создан с той
же collation, что и `ORDER BY`, иначе PostgreSQL его не использует, и keyset
начинает возвращать неверные границы. Фиксируем collation явно в миграции.

## 7.6. Найдено при подготовке плана: многоуровневая сортировка тоже клиентская

**Факт.** Бэкенд поддерживает сортировку **по одному полю**:

```python
# backend/src/catalog/application/dto.py
@dataclass(frozen=True)
class Ordering:
    field: str = "reviews_count"
    descending: bool = True
```

`parse_ordering` читает один параметр `?ordering=`. При этом
[SortBuilder.tsx](../../frontend/src/components/Filters/SortBuilder.tsx)
собирает **произвольное число уровней** и имеет пресеты со смешанными
направлениями, а `buildProductsQuery` отправляет на сервер только первый
уровень.

**Вывод.** Многоуровневая сортировка сегодня выполняется на клиенте, поверх той
же выборки в тысячу строк. Это третий случай одной и той же причины — вместе с
пагинацией и гистограммами (док. 2, §2.3).

**Следствия для плана:**

1. Отклонение П1 расширяется: на сервер переезжает не только пагинация, но и
   многоуровневая сортировка. Иначе серверная страница будет отсортирована
   иначе, чем ожидает интерфейс, — а это уже потеря паритета.
2. `Ordering` перестаёт быть парой «поле + направление» и становится списком
   ключей. **Это единственная санкционированная правка в `application/`**;
   критерий выхода фазы 1 «ноль правок в domain/application» получает явное
   исключение, зафиксированное здесь.
3. `ORDERABLE_FIELDS` (`price`, `sale_price`, `rating`, `reviews_count`,
   `name`) не меняется — расширяется только структура, не словарь полей.
4. Валидация «поле встречается не более одного раза» переезжает на сервер;
   сейчас её обеспечивает интерфейс, отключая уже использованные поля в
   выпадающем списке.

Изменение обратно совместимо: одиночный `?ordering=-reviews_count` остаётся
рабочим и трактуется как список из одного ключа.

их прохождения понадобилось править `domain/` или `application/` где-либо,
кроме `Ordering`, — остановиться и пересмотреть оценку программы (риск R2).
