# 4. Технологический стек

Принцип отбора: **асинхронность по умолчанию, зрелость важнее новизны,
эксплуатационная сложность — тоже цена.** Каждая позиция сопровождена причиной
выбора и, где уместно, отвергнутой альтернативой.

Скоуп — миграция без новых функций, поэтому из стека убрано всё, что
обслуживало отменённые возможности: ML-библиотеки, Keycloak, Feast.

## 4.1. Язык и рантайм

| Позиция | Выбор | Почему |
|---|---|---|
| Язык | Python 3.13 | Весь домен уже на Python; 3.13 заметно быстрее на интерпретации |
| Веб-фреймворк | FastAPI ≥ 0.115 (Starlette) | Нативный ASGI, DI из коробки, OpenAPI 3.1 генерируется из типов |
| Сервер | Uvicorn с `uvloop` + `httptools` под Gunicorn | Проверенная связка; Granian рассматривать после нагрузочных тестов, не до |
| Валидация | Pydantic v2 | Ядро на Rust, ~15-20× быстрее v1; на горячем пути сериализации это решает |
| Пакеты | `uv` | Установка на порядок быстрее pip, воспроизводимый lock |
| Качество | `ruff` + `mypy --strict` | ruff уже в проекте; strict-типизация обязательна для домена |
| DI | `dishka` | Async-scopes, ложится на нынешний подход «composition root на контекст» |
| JSON | `orjson` | В 2-3 раза быстрее stdlib на ответах Wildberries |

Отвергнуто: **Litestar** (быстрее на бенчмарках, но экосистема и найм хуже),
**Go/Rust для ingestion** (выигрыш реален, но сбор упирается в лимиты площадки,
а не в CPU — преждевременная оптимизация ценой второго языка в команде).

## 4.2. Хранилища

| Назначение | Выбор | Почему |
|---|---|---|
| OLTP | PostgreSQL 16, отдельная БД на сервис | Уже используется; RLS, `SKIP LOCKED`, партиционирование — всё нужное есть |
| Драйвер | `asyncpg` через SQLAlchemy 2.0 (async) | Самый быстрый асинхронный драйвер PostgreSQL |
| Миграции | Alembic | Стандарт для SQLAlchemy, поддерживает и автогенерацию, и ручные правки |
| Пул | PgBouncer, transaction mode | Обязателен: без него каждый под держит свой пул и `max_connections` кончается |
| Ряды и агрегаты | ClickHouse 24.x | Колоночное сжатие 10-30×, TTL, партиции по месяцам, `ReplacingMergeTree` |
| Драйвер CH | `clickhouse-connect` (async) | Официальный, поддерживает батч-вставку и стриминг |
| Кэш, лимиты, локи | Redis 7 (Sentinel в проде) | Уже используется; `redis-py` в async-режиме |
| Объекты | S3 / MinIO | Артефакты выгрузок |

> **Подводный камень.** PgBouncer в transaction mode несовместим с prepared
> statements asyncpg. Обязательно `statement_cache_size=0` и
> `prepared_statement_cache_size=0` в строке подключения, иначе будут плавающие
> `prepared statement "__asyncpg_..." already exists` — воспроизводятся под
> нагрузкой и не воспроизводятся в dev.

Отвергнуто: **TimescaleDB** — проще в эксплуатации (расширение PostgreSQL), но
на сканировании больших объёмов проигрывает колоночному хранилищу в разы.
Решение по ClickHouse подтверждено; архитектура допускает замену — меняется
только адаптер в `timeseries-service`.

## 4.3. Обмен сообщениями и фоновая работа

| Назначение | Выбор | Почему |
|---|---|---|
| Событийная шина | **Apache Kafka 4.x в режиме KRaft** | ZooKeeper удалён из Kafka 4.0; KRaft — единственный поддерживаемый режим и меньшая эксплуатационная поверхность |
| Клиент | `aiokafka` | Асинхронный, ручной коммит офсетов |
| Схемы | Confluent Schema Registry + Protobuf | Строгий контракт между сервисами, BACKWARD-совместимость |
| Линтер схем | `buf` | Проверка обратной совместимости `.proto` в CI |
| Очередь задач | **Taskiq** поверх Kafka | Async-native; Celery остаётся синхронным по своей природе |
| Планировщик | Собственный на `SELECT … FOR UPDATE SKIP LOCKED` | Несколько реплик безопасны, нет единой точки отказа (дефект H7) |

### Что означает выбор KRaft

KRaft объявлен production-ready в Kafka 3.3, ZooKeeper-режим объявлен
устаревшим в 3.5 и **удалён в 4.0**. Выбор KRaft — это выбор поддерживаемой
линии, а не ранней технологии: обратный вариант зафиксировал бы кластер на
3.9.x с известной датой конца поддержки.

Практические следствия:

- **Одна система вместо двух.** Метаданные живут во внутреннем топике
  `__cluster_metadata`, реплицируемом Raft-кворумом контроллеров. Нет
  отдельного ансамбля ZooKeeper, нет его мониторинга, нет его дисков и ACL.
- **Кворум контроллеров — три узла** (`controller.quorum.voters`). В
  продакшене контроллеры выносятся в отдельные поды (`process.roles=controller`),
  брокеры — `process.roles=broker`. Совмещённый режим
  (`broker,controller`) допустим только в dev.
- **Метаданные — на быстрый диск.** `metadata.log.dir` отдельно от
  журналов топиков: Raft-лог чувствителен к латентности `fsync`, и общий диск
  с горячим топиком даёт переизбрания контроллера.
- **`storage format` при первом запуске.** Кластер инициализируется
  `kafka-storage.sh format --cluster-id …` — шаг обязательный и
  единоразовый, его место в Helm-хуке, а не в ручной инструкции.
- **Dev-окружение становится одним контейнером** — Kafka в совмещённом режиме
  без ZooKeeper. `docker compose` на пять сервисов короче.
- **Проверить `aiokafka` на совместимость с 4.x** до фазы 2: Kafka 4.0 убрала
  старые версии протокольных API. Это пункт чек-листа, а не ожидаемая проблема.

Одна необратимая операция, о которой нужно знать заранее: **повышение
`metadata.version`** (через `kafka-features upgrade`) откатить нельзя.
Поэтому версия метаданных поднимается отдельным осознанным шагом после
обновления брокеров, а не автоматически вместе с ним. Зафиксировано как риск
R12 в [док. 6](06-risks.md).

Отвергнуто: **Celery** (работает, но синхронный пул — весь смысл перехода на
async теряется на воркерах), **RabbitMQ** (хорошая очередь, но нужен именно
лог событий с реплеем и несколькими консьюмер-группами), **Temporal**
(правильный инструмент для долгих оркестраций; при однoшаговом сборе — лишняя
инфраструктура).

## 4.4. Сеть и сбор данных

| Позиция | Выбор | Отношение к текущему коду |
|---|---|---|
| HTTP-клиент | **`aiohttp`** | Заменяет `httpx`: async-native, без синхронного слоя |
| Мок HTTP в тестах | **`aioresponses`** | Заменяет `respx` — тот привязан к `httpx` |
| Повторы | `tenacity` | Заменяет ручной цикл backoff, поведение сохраняется |
| Лимиты | `aiolimiter` | Token bucket, адаптивный по `429` — новое, необходимое при параллелизме |
| Circuit breaker | `purgatory` | Новое: без него параллельный сбор долбит упавшую площадку |
| Ротация UA | Переносится как есть | Логика `itertools.cycle` из нынешнего гейтвея |
| Пул соединений | `TCPConnector(limit, limit_per_host)` | Штатная замена ручному семафору |

### Почему aiohttp, и что это стоит

`httpx` спроектирован как синхронная библиотека с добавленным async-слоем;
`aiohttp` async-native изначально. На профиле «много одновременных исходящих
запросов к одному хосту» — а это ровно профиль `ingestion-service` — разница в
накладных расходах заметна.

**Побочная выгода, снимающая нынешнее ограничение.** В `httpx` прокси задаётся
при создании клиента, поэтому текущий гейтвей выбирает **один прокси на весь
прогон** ([gateway.py:58](../../backend/src/catalog/adapters/outbound/wildberries/gateway.py:58)).
В `aiohttp` прокси — аргумент запроса, значит ротация становится поштучной.
Для обхода антибот-защиты при параллельном сборе это принципиально.

**Цена.** `respx` — мок именно для `httpx`, и на нём построены офлайн-тесты
шлюза WB (`tests/adapters/test_wb_gateway.py`,
`test_wb_gateway_resilience.py`). Их придётся переписать на `aioresponses`.
Фикстура `tests/fixtures/wb_search.json` переносится без изменений, то есть
переписывается обвязка, а не проверяемое поведение. Оценка — 1-2 дня, риск R13
в [док. 6](06-risks.md).

`TCPConnector(limit=…, limit_per_host=…)` заменяет ручной `asyncio.Semaphore`
и заодно даёт переиспользование keep-alive соединений — при постраничном
обходе одного хоста это уменьшает число TLS-рукопожатий до одного на прогон.

## 4.4a. Взаимодействие между сервисами

Основной путь обмена — **асинхронный, через Kafka**. Синхронные вызовы
допускаются только там, где нужен ответ здесь и сейчас, и для них принят
**gRPC**; REST остаётся исключительно на внешнем периметре.

| Направление | Протокол | Обоснование |
|---|---|---|
| Браузер и внешние клиенты → `api-gateway` | REST `/v1` + WebSocket | Публичный контракт, OpenAPI, кэшируемость |
| `api-gateway` → доменные сервисы | **gRPC** | Типизированный контракт, HTTP/2-мультиплексирование, низкая латентность на агрегации BFF |
| Сервис → сервис (синхронно) | **gRPC** | То же; список мест — ниже |
| Сервис → сервис (асинхронно) | Kafka + Protobuf | Основной путь: события, проекции, алерты |

**Где синхронные вызовы действительно нужны** — список исчерпывающий, всё
остальное идёт событиями:

1. `api-gateway` → любой сервис — обслуживание пользовательского запроса.
2. `export` → `catalog` — вычитка отфильтрованной выборки под выгрузку.
   Здесь используется **server-streaming gRPC**: строки идут потоком, а не
   собираются в память ни на одной стороне.
3. `notifications` → `catalog` — название товара для текста уведомления.
   Unary-вызов с кэшем в Redis.

| Позиция | Выбор | Почему |
|---|---|---|
| Реализация | `grpcio` + `grpcio-tools`, asyncio-API (`grpc.aio`) | Официальная, поддерживает streaming и interceptors |
| IDL | Protobuf 3 | **Тот же язык описания, что у событий** — одна схема, один генератор, один линтер |
| Проверка совместимости | `buf breaking` в CI | Ломающее изменение `.proto` не проходит пайплайн |
| Health checks | gRPC Health Checking Protocol | Штатные `readinessProbe` в Kubernetes через `grpc_health_probe` |
| Трассировка | OTel gRPC-интерцепторы | `traceparent` в metadata, трасса не рвётся |
| Ошибки | `google.rpc.Status` + `grpc-status-details-bin` | Единая модель ошибок, отображается в конверт REST на шлюзе |

Отвергнут **REST между сервисами**: работает, но контракт пришлось бы держать
отдельной дисциплиной (JSON Schema или OpenAPI на каждую пару), тогда как
Protobuf уже введён ради событий. Один IDL на всю систему дешевле двух.

> **Следствие для тестирования.** `pact-python` плохо покрывает gRPC. Роль
> контрактных тестов для синхронных вызовов берёт на себя `buf breaking` плюс
> интеграционные тесты на testcontainers; `pact` остаётся для REST-периметра.

## 4.5. Аутентификация и безопасность

| Позиция | Выбор | Почему |
|---|---|---|
| Токены | JWT RS256 с ротацией ключей, JWKS-эндпоинт | Верификация в шлюзе по публичному ключу, без похода в БД на каждый запрос |
| Google-вход | `Authlib` + `google-auth` | `google-auth` уже используется, проверка ID-токена переносится |
| Хеш паролей | `argon2-cffi` | Заменяет PBKDF2 из Django; современный стандарт |
| Отзыв сессии | Список отзыва refresh-токенов в Redis | Заменяет `token_blacklist` в PostgreSQL — запрос на каждый refresh уходит |
| Ingress | Traefik v3 | TLS, ACME, rate-limit; конфигурация декларативная |
| Секреты | Vault + External Secrets Operator | Ни одного секрета в манифестах |
| Заголовки | CSP, HSTS, `X-Content-Type-Options`, `Referrer-Policy` | Переносится `config/security_headers.py` |
| Сканирование | `pip-audit`, Trivy на образы, gitleaks в pre-commit | Обязательный gate в CI |

**Keycloak отвергнут.** Он был нужен ровно ради SAML и SCIM — то есть ради
функциональности, которая из скоупа исключена. Для пароля и Google ID-токена
собственный `identity-service` на ~400 строк дешевле в разработке и
несопоставимо дешевле в эксплуатации, чем отдельный Java-сервис с собственной
БД и моделью обновлений. Когда SSO понадобится — Keycloak встанет за
`identity-service` без изменения контракта.

## 4.6. Наблюдаемость

| Слой | Выбор |
|---|---|
| Инструментация | OpenTelemetry SDK — авто-инструментация FastAPI, SQLAlchemy, aiokafka, aiohttp, grpcio, redis |
| Метрики | Prometheus; дашборды RED на сервис, USE на инфраструктуру |
| Логи | `structlog` → JSON → Loki; обязательные поля `trace_id`, `service`, `owner_id` |
| Трассировка | Tempo (Jaeger в dev) |
| Ошибки | Sentry |
| Визуализация | Grafana, единый набор дашбордов на сервис |

`trace_id` протягивается через Kafka в заголовках сообщения и через gRPC в
metadata. Без этого трасса рвётся на границе события — самая частая ошибка при
вводе шины, и закрывать её нужно в `libs/platform`, а не в каждом сервисе.

К дашбордам добавляется набор по **кворуму контроллеров KRaft**: активный
лидер, лаг реплик `__cluster_metadata`, частота переизбраний. Частые
переизбрания — первый признак того, что `metadata.log.dir` делит диск с
горячим топиком.

## 4.9. Фронтенд

Переписывать не нужно — 7 426 строк React 18 + TS остаются. Меняется ровно то,
что затронуто тремя отклонениями от паритета
([док. 2, §2.3](02-functional-parity.md)):

| Позиция | Выбор | Зачем |
|---|---|---|

| Гистограммы | Данные с сервера вместо `lib/histogram.ts` | Отклонение П1 |
| Экспорт | Опрос статуса задания | Отклонение П2 |
| Прогресс сбора | WebSocket | Отклонение П3 |
| Кодоген | `openapi-typescript` из `/v1/openapi.json` | Типы клиента генерируются из контракта |

`TanStack Virtual` **не нужен**: при серверной пагинации в таблице максимум
100 строк, и виртуализировать нечего. Recharts остаётся — при серверной
агрегации на график приходит десяток корзин, а не тысяча точек.

│   ├── grpc/*.proto         внутренние сервисные интерфейсы

│   ├── api_gateway/

Внутри каждого сервиса сохраняется нынешняя структура — `domain/`,
`application/`, `adapters/{inbound,outbound}/`, `composition/`. Гексагон никуда
не девается; переписывается только то, что лежит в `adapters/`.
