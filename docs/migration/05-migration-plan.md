# 5. План миграции

## 5.1. Стратегия: Strangler Fig, а не переписывание

Django остаётся работающим и обслуживающим трафик до последней фазы; маршруты
переезжают на FastAPI по одному, за обратным прокси. В любой момент откатывается
один маршрут, а не вся система.

Три правила на всю программу:

1. **Контракт API заморожен.** Единственные допустимые отклонения — три,
   перечисленные в [док. 2, §2.3](02-functional-parity.md). Любое другое
   расхождение с `contracts/openapi/v1.yaml` — красный CI.
2. **Сначала швы, потом сервисы.** Пока `analytics` импортирует `ProductModel`,
   выносить его бессмысленно. Порядок: разорвать связи → делить процессы.
3. **Домен переносится копированием.** Правка в `domain/` или `application/` —
   повод остановиться и разобраться, а не признак прогресса.

### §0.1. Снятие контракта: проблема и решение

`drf-spectacular` в проект не установлен, и просто добавить его недостаточно.
Все вьюхи — голые `APIView`, которые собирают ответ вручную:

```python
# catalog/adapters/inbound/http/views.py
return Response({"count": …, "next": None, "previous": None, "results": results})
```

Ни `serializer_class`, ни `queryset` у них нет, параметры фильтров читаются
вручную в `parse_product_filter`. Генератору схемы не за что зацепиться: он
выдаст эндпоинты с пустыми телами ответов и без единого query-параметра. Такой
файл нельзя использовать как эталон — `schemathesis` по нему ничего не
проверит.

**Что делается — четыре шага.**

**Шаг 1. Дописать недостающие сериализаторы ответов.** Сейчас часть ответов —
анонимные словари; для них классов просто нет:

| Ответ | Где собирается вручную | Новый класс |
|---|---|---|
| `{count, next, previous, results}` | `ProductListView.get` | `ProductPageSerializer` |
| `{task_id, query, status}` | `ParseView.post` | `ParseEnqueuedSerializer` |
| `{wb_id, points}` | `HistoryView.get` | `PriceHistorySerializer` |
| `{items: [{query, stats}]}` | `StatsView.get` (ветка сравнения) | `QueryComparisonSerializer` |
| `{detail}` | обработчик исключений, 400/404/502 | `ErrorSerializer` |

Существующие `ProductViewSerializer`, `ParseJobSerializer`, `StatsSerializer`,
`SnapshotSerializer`, `ScheduleSerializer`, `AlertRuleSerializer` уже пригодны и
переиспользуются.

**Шаг 2. Разметить вьюхи `@extend_schema`.** Явно объявляются `request`,
`responses` (включая коды ошибок) и `parameters`. Логика вьюх при этом не
меняется — только аннотации.

**Шаг 3. Query-параметры объявить один раз и защитить от расхождения.**
Ключевой момент. `parse_product_filter` и `parse_ordering` читают параметры
вручную, и если продублировать их список в `@extend_schema`, две копии
разъедутся при первой же правке.

Поэтому список параметров выносится в один модуль
(`catalog/adapters/inbound/http/schema_params.py`), откуда его берёт
`@extend_schema`, и добавляется тест, сверяющий объявленные имена с ключами,
которые парсер фактически читает. Расхождение падает в CI, а не всплывает в
спеке.

Валидацию **не** переписываем на сериализаторы: сообщения `InvalidFilter`
зафиксированы существующими тестами, и менять их сейчас — риск потерять паритет
там, где выигрыша нет.

**Шаг 4. `ExportView`** возвращает файл, а не JSON — описывается как
`OpenApiTypes.BINARY` с двумя content-type (`text/csv`,
`application/vnd.openxmlformats-…`).

**Проверка результата:**

```bash
python manage.py spectacular --file contracts/openapi/v1.yaml --validate --fail-on-warn
```

`--fail-on-warn` обязателен: без него spectacular молча проглатывает
неразмеченные вьюхи и выдаёт неполную спеку — ровно тот файл, который выглядит
рабочим и ничего не проверяет.

**Оценка:** 2-3 дня. Побочная выгода — спека покрывает и нынешний Django, что
даёт `schemathesis` возможность гонять один набор тестов против обеих
реализаций на фазе 1.

      `getPaginationRowModel` убирается, `PAGE_SIZE = 1000` уходит

      только в фазе 5, и тогда же этот REST станет внутренним gRPC.
- [ ] `schemathesis` против обеих реализаций — ответы обязаны совпасть.
- [ ] Канареечный вывод: 5 % → 50 % → 100 %.

**Выход:** каталог обслуживается FastAPI в проде.

## 5.3. Что можно сократить

Гранулярность (9 сервисов) и хранилище (ClickHouse) зафиксированы. Остаётся:

1. **Отложить фазу 6** до первого продакшн-инцидента — но тогда девять
   сервисов выкатываются без автоскейла и контрактных тестов. Не рекомендую.
2. **Схлопнуть `export` в `analytics` и `scheduling` в `ingestion`** —
   экономит ~1 неделю, границы и контракты это позволяют без переписывания.
3. **Оставить offset-пагинацию** на первом этапе — экономит несколько дней
   и работу на фронтенде, но не снимает дефект H6.

Чего резать **нельзя**: фазу 0 (без замороженного контракта миграция
неуправляема), transactional outbox (без него потеря событий — вопрос времени,
а не вероятности), `libs/platform` и шаблон сервиса (на девяти сервисах
дублирование неуправляемо), двойную запись со сверкой в фазе 3 (единственный
способ убедиться, что бэкфилл не потерял историю).
