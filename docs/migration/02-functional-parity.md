# 2. Функциональный паритет

Скоуп программы — **миграция без изменения функциональности**. Новые
продуктовые возможности из обсуждения исключены. Этот документ фиксирует, что
именно должно работать после миграции точно так же, как работает сейчас, и в
каком сервисе окажется каждая возможность.

Он же является **чек-листом приёмки**: миграция завершена, когда все строки
таблиц ниже отмечены и контрактные тесты зелёные.

## 2.3. Три места, где паритет невозможен буквально

Это не расширение функциональности, а следствие требований highload. Каждое
изменение сохраняет то, что видит пользователь, и меняет то, как это устроено.

### П1. Пагинация, сортировка и гистограммы переезжают на сервер

**Сейчас — и это дефект, а не только вопрос производительности.**
[buildProductsQuery](../../frontend/src/api/products.ts) не передаёт ни `page`,
ни `page_size`: фронтенд забирает всю выборку до потолка
`REST_FRAMEWORK.PAGE_SIZE = 1000` и листает её в браузере через
[getPaginationRowModel()](../../frontend/src/components/ProductTable.tsx:148).
Интерфейс это честно признаёт надписью «первые N из M» в
[TablePagination.tsx](../../frontend/src/components/TablePagination.tsx).

**Следствие для пользователя сегодня:** если выборка больше тысячи товаров,
всё за её пределами **недостижимо** — ни листанием, ни сортировкой. Кнопка
«последняя страница» ведёт на тысячную строку, а не на последнюю.

Гистограммы построены на том же допущении:
[PriceHistogram.tsx](../../frontend/src/components/charts/PriceHistogram.tsx)
и [DiscountVsRatingChart.tsx](../../frontend/src/components/charts/DiscountVsRatingChart.tsx)
считают распределения на клиенте из полученного массива — то есть по первой
тысяче строк, а не по выборке.

**Многоуровневая сортировка — третий случай той же причины.** Бэкенд
поддерживает сортировку **по одному полю**: `Ordering` — это пара
`field` + `descending`, а `parse_ordering` читает один параметр `?ordering=`.
При этом [SortBuilder.tsx](../../frontend/src/components/Filters/SortBuilder.tsx)
собирает произвольное число уровней и содержит пресеты со смешанными
направлениями («Дешевле ↑ + рейтинг ↓»), а `buildProductsQuery` отправляет на
сервер только первый уровень. Остальные уровни применяются в браузере — снова
поверх той же тысячи строк.

**Решение.**

1. **Пагинация становится серверной.** `GET /v1/products` отдаёт страницу
   запрошенного размера (10/25/50/100 — те же варианты, что в интерфейсе
   сейчас) с keyset-курсором. Таблица переводится на
   `manualPagination: true`, `getPaginationRowModel` убирается.
2. **Сортировка становится серверной и многоуровневой.** `Ordering`
   превращается в список ключей; клиент передаёт все уровни, а не первый.
   Без этого серверная страница будет отсортирована иначе, чем ожидает
   интерфейс, — и паритет потеряется. Это **единственная санкционированная
   правка в `application/`**, обоснование —
   [док. 7, §7.6](07-implementation-plan.md).
3. **Гистограммы считаются в `analytics-service`.** Два новых эндпоинта,
   агрегация в ClickHouse по всей отфильтрованной выборке; клиент получает
   готовые корзины.

**Что видит пользователь.** Те же элементы управления и те же графики, но
листание доходит до конца выборки, а распределения строятся по всем товарам, а
не по первой тысяче. Это не потеря паритета, а устранение скрытого ограничения.

**Затрагивает.** `frontend/src/api/products.ts` (курсор и размер страницы),
`components/ProductTable.tsx` (ручная пагинация), `lib/histogram.ts`
(удаляется), оба компонента графиков, `api/stats.ts`.
`TanStack Virtual` не требуется — на странице не больше 100 строк.

### П2. Экспорт становится асинхронным

**Сейчас.** `GET /api/export/?format=xlsx` собирает файл в памяти процесса
(`build_xlsx`) и отдаёт в том же запросе. CSV уже потоковый.

**Проблема.** На выборке в сотни тысяч строк XLSX в памяти кладёт процесс,
а HTTP-запрос упирается в таймаут балансировщика.

**Решение.** `POST /v1/exports` возвращает `202` и идентификатор; файл
генерируется потоково в S3; клиент забирает по presigned-URL. Кнопки экспорта
в интерфейсе получают индикатор готовности.

**Затрагивает.** `frontend/src/components/ExportButtons.tsx`, `api/export.ts`.

### П3. Согласованность в конечном счёте

**Сейчас.** Сбор завершается — статистика доступна немедленно: событие
доставляется синхронно, в той же транзакции.

**Проблема.** С брокером между сервисами появляется задержка 1-5 секунд.
Пользователь увидит «сбор завершён», а цифры ещё старые.

**Решение.** Прогресс сбора через WebSocket с явными стадиями: «собрано →
сохранено → готово к анализу». Интерфейс ждёт последнюю стадию, а не первую.

**Затрагивает.** `frontend/src/hooks`, `api/parse.ts`, `api/tasks.ts`.

## 2.4. Что сознательно НЕ входит в скоуп

Зафиксировано, чтобы не расползлось по ходу работы:

- Организации, роли, SSO, SCIM, журнал аудита
- Мультиарендность (`tenant_id`) — см. решение в [§3.1](03-target-architecture.md)
- Вторая торговая площадка
- Отслеживание позиций в выдаче, остатки, доля полки
- Машинное обучение в любом виде
- Юнит-экономика, мониторинг карточки, контроль RRP/MAP
- Публичное API с ключами и квотами, вебхуки, SDK
- Выгрузки в BI-системы

Архитектура из [док. 3](03-target-architecture.md) не закрывает дорогу ни к
одному из этих пунктов, но и не платит за них заранее.
