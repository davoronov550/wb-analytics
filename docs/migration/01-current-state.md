# 1. Анализ текущей архитектуры

> Состояние на коммит `00aa21c`. Все ссылки — на реальные файлы репозитория.

## 1.1. Габариты

| Часть | Строк | Комментарий |
|---|---:|---|
| `backend/src` | 4 479 | 6 ограниченных контекстов |
| `backend/tests` | 3 086 | 184 теста, покрытие 94 % |
| `frontend/src` | 7 426 | React 18 + TS + Vite, 37 тестов |

Распределение по контекстам: `catalog` 1 501 · `analytics` 886 · `accounts` 702 ·
`notifications` 639 · `scheduling` 442 · `shared` 309.

Это **небольшая, очень аккуратно написанная система**. Главный вывод анализа:
переписывать нужно не бизнес-логику, а исключительно инфраструктурный слой.

## 1.2. Что сделано правильно и переезжает без изменений

Гексагональная архитектура здесь не декоративная, а работающая:

- `domain/` и `application/` **не импортируют ни Django, ни DRF, ни httpx, ни Celery**.
  Проверяется тестами вида `pytest -m "not django_db"` — 149 тестов проходят без
  инфраструктуры вообще.
- Порты объявлены как `typing.Protocol` (`shared/application/ports.py`,
  `catalog/application/ports/outbound.py`) — структурная типизация, адаптер не
  импортирует порт.
- У каждого контекста единственный корень сборки — `<context>/composition/container.py`.
- Value objects (`Money`, `Rating`, `ReviewsCount`) валидируют инварианты в
  конструкторе; есть отдельные `coerce`-парсеры для грязных данных WB.
- События (`shared/events.py`) — иммутабельные dataclass'ы с примитивными полями,
  специально пригодные к сериализации.

**Практический эффект для миграции:** ~1 800 строк доменного и прикладного кода
переносятся в FastAPI-сервисы копированием, без правок. Переписывается только
`adapters/` и `composition/`. Это сокращает объём работы примерно вдвое против
миграции с типичного Django-проекта.

## 1.3. Блокеры распила на сервисы

Три места нарушают изоляцию контекстов. Пока они есть, вынести сервис нельзя.

### Б1. `analytics` читает таблицу `catalog` напрямую

```
analytics/adapters/outbound/catalog_reader.py:11   from catalog.adapters.outbound.persistence.models import ProductModel
analytics/adapters/outbound/stats_query.py:22      from catalog.adapters.outbound.persistence.models import ProductModel
```

Это shared database между контекстами. Вся статистика (`/api/stats/`) — агрегаты
поверх чужой таблицы. При разнесении по сервисам сломается сразу.

### Б2. `scheduling` вызывает `catalog` внутрипроцессно

```
scheduling/adapters/outbound/catalog_enqueuer.py:12  from catalog.composition import container as catalog_container
```

Прямой вызов composition root чужого контекста вместо публикации события.

### Б3. Шина событий — синхронная и без брокера

`shared/adapters/event_bus.py` доставляет событие вызовом обработчика в том же
стеке и той же транзакции. `shared/adapters/message_bus.py`, который включается
через `EVENT_PUBLISHER=bus`, — **заглушка**: он пишет `logger.info` и вызывает
локальных подписчиков. Реального брокера нет.

Следствия: нет at-least-once, нет повторов, нет порядка, нет реплея; исключение
в подписчике роняет публикатора; событие теряется при падении процесса между
записью в БД и публикацией (нет transactional outbox).

## 1.4. Дефекты, критичные под нагрузкой

### H1. Всё синхронное

WSGI (`config/wsgi.py`), синхронный `psycopg`, синхронный `httpx.Client`.
Пропускная способность упирается в число процессов/потоков. Воркер, ждущий
ответа Wildberries 3 секунды, всё это время занят целиком.

### H2. Сбор страниц последовательный

`catalog/adapters/outbound/wildberries/gateway.py:59` — цикл `for page in range(1, max_pages + 1)`
с синхронным `client.get`. При `max_pages=10` и 1 с на страницу сбор одного
запроса занимает ≥10 с и полностью блокирует воркер.

### H3. N+1 в записи снимков

`analytics/application/use_cases/record_snapshots.py:31` — на каждый товар
отдельный `repository.last(wb_id)` и отдельный `repository.add(...)`.
Сбор 1 000 товаров = ~2 000 запросов к PostgreSQL.

### H4. OLAP-нагрузка на OLTP-базе

`analytics/adapters/outbound/stats_query.py` считает `AVG`, `STDDEV`,
`PERCENTILE_CONT`, `COUNT(*) FILTER` по `catalog_product` на каждый вызов
`/api/stats/` (кэш в Redis смягчает, но не решает). Гистограммы и сравнение
запросов — там же. На десятках миллионов строк это деградирует.

### H5. Таблица временных рядов не партиционирована

`analytics_snapshot` — append-only, растёт линейно от числа товаров × число
сборов, без партиций, без TTL, без сжатия. Это главный кандидат на переезд в
колоночное хранилище.

### H6. OFFSET-пагинация

`page`/`page_size` через `OFFSET` (README сам это фиксирует как долг).
`REST_FRAMEWORK.PAGE_SIZE = 1000` (`config/settings.py:150`) — «графикам нужен
весь набор», то есть один запрос может тянуть 1 000 строк.

### H7. Планировщик — единственный процесс

Celery Beat опрашивает БД раз в 60 с. Нет leader election и распределённой
блокировки: два экземпляра beat дадут двойной сбор, один упавший — остановку
всех расписаний.

### H8. Redis как брокер Celery

Redis-брокер не даёт durability-гарантий при failover; result backend тоже в
Redis. Для enterprise-SLA этого недостаточно.

## 1.5. Дефекты эксплуатационной зрелости

Скоуп программы — миграция без новых функций, поэтому организации, SSO,
мультиарендность и вторая торговая площадка сюда не входят
([док. 2, §2.4](02-functional-parity.md)). Остаются дефекты, которые мешают
эксплуатировать даже нынешнюю функциональность.

### E1. Нет наблюдаемости

Единственный инструмент — `/api/health/` (проверка БД и Redis). Нет метрик,
нет трассировки, нет correlation-id, нет структурных логов. Диагностика
инцидента в проде сводится к чтению stdout.

Это самый серьёзный дефект списка: девять сервисов без трассировки
неотлаживаемы в принципе.

### E2. API не готов к версионированию

Пути без версии (`/api/products/`, не `/v1/products`), формат ответа
неунифицирован между эндпоинтами, нет OpenAPI-спецификации как контракта.
Идемпотентность `POST /api/parse/` держится на поиске активной задачи в БД
(`find_active(query)`), а не на `Idempotency-Key` — она защищает от
одновременных запросов с одинаковым текстом, но не от повтора после таймаута.

### E3. Изоляция владельца — только в коде

`filter(owner_id=…)` в репозиториях покрыт тестами, и это лучше, чем проверка
во вьюхе. Но RLS на `accounts_saved_search`, `notifications_alert_rule` и
`scheduling_schedule` нет — README сам числит это в рекомендациях для
продакшена. Ошибка в одном запросе даёт утечку между пользователями.

### E4. Жёсткая привязка к одной площадке

`wb_id` как глобально уникальный ключ вшит в модель, API и фронтенд.
Переход на составной `(marketplace, external_id)` стоит почти ноль, если
сделать его в фазе 1, и дорого — если когда-нибудь потом.

Связанный дефект: `source_query` — внешний ключ, который **перезатирается**
последним сбором, поэтому товар, найденный по двум запросам, теряет привязку
к первому. Поведение сохраняется как есть (это функциональный паритет), но
знать о нём нужно.

## 1.6. Сводка

| Категория | Оценка |
|---|---|
| Доменная модель и прикладной слой | Готовы к переносу, правок не требуют |
| Тесты домена и сценариев | Переносятся вместе с кодом |
| Изоляция контекстов | 3 нарушения, все локальные (Б1-Б3) |
| Инфраструктурный слой | Переписывается полностью |
| Модель данных | Переезжает почти как есть; ключ `wb_id` → `(marketplace, external_id)` |
| Наблюдаемость и эксплуатация | Отсутствуют, разрабатываются с нуля |
| Мультиарендность и SSO | Вне скоупа — см. [док. 3, §3.1](03-target-architecture.md) |
