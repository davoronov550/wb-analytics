# Feature Specification: Wildberries Product Analytics Service

**Feature Branch**: `001-wb-product-analytics`

**Created**: 2026-08-07

**Status**: Draft (scope expanded 2026-08-07 to include FE-01..FE-09)

**Input**: A Wildberries market-analytics service. Core: parse products by query
(name, price, sale price, rating, reviews), store them, expose `GET /api/products/`
with filtering, and a web UI with a filterable/sortable table plus a price
histogram and a discount-vs-rating chart. Expanded scope adds: scheduled parsing,
asynchronous collection, parser resilience, price history, extended analytics,
query comparison, price alerts, data export, and authentication with saved searches.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Collect products by query (Priority: P1)

Аналитик вводит поисковый запрос/категорию и запускает сбор; система обходит
выдачу Wildberries, извлекает по каждому товару название, цену, цену со скидкой,
рейтинг, число отзывов и сохраняет в БД.

**Why this priority**: фундамент — без данных нет ни таблицы, ни аналитики.

**Independent Test**: запустить сбор по запросу → в БД товары с 5 полями; повторный
запуск не создаёт дублей, а обновляет.

**Acceptance Scenarios**:

1. **Given** пустая база, **When** сбор по «наушники», **Then** сохранены товары с 5 полями.
2. **Given** товар уже сохранён, **When** повтор сбора, **Then** запись обновлена, не задвоена.
3. **Given** товар без рейтинга/отзывов, **When** разбор, **Then** поля = 0/пусто, запись не теряется, сбой одного товара не рушит сбор.

---

### User Story 2 - Table with filters & sorting (Priority: P1)

Пользователь видит таблицу (название, цена, цена со скидкой, рейтинг, отзывы),
фильтрует слайдером диапазона цен, минимальным рейтингом и минимумом отзывов,
сортирует по колонкам; таблица перерисовывается динамически.

**Why this priority**: основной рабочий интерфейс; вместе с US1 — MVP.

**Independent Test**: на заполненной БД применить `min_price/max_price`, `min_rating`,
`min_reviews` и сортировку — состав и порядок строк соответствуют условиям.

**Acceptance Scenarios**:

1. **Given** данные есть, **When** загрузка, **Then** таблица из 5 колонок.
2. **Given** таблица, **When** слайдер 5000–10000, **Then** только товары в диапазоне (по цене со скидкой).
3. **Given** таблица, **When** рейтинг ≥4.0 и отзывы ≥100, **Then** только удовлетворяющие оба условия.
4. **Given** таблица, **When** клик по «Цена», **Then** сортировка asc, повторный клик — desc.
5. **Given** активны фильтры, **When** смена фильтра, **Then** таблица и графики обновляются без перезагрузки.

---

### User Story 3 - Analytics charts (Priority: P2)

Две диаграммы по текущей (отфильтрованной) выборке: гистограмма распределения цен
и линейный график «скидка vs рейтинг»; пересчитываются при смене фильтров.

**Why this priority**: заявленная цель, но надстройка над US1/US2.

**Independent Test**: сумма столбцов гистограммы = числу строк таблицы; точки графика
= парам (скидка, рейтинг) видимых товаров. Компоненты тестируются на mock-данных.

**Acceptance Scenarios**:

1. **Given** выборка, **When** отрисовка, **Then** гистограмма количества по ценовым диапазонам.
2. **Given** выборка, **When** отрисовка, **Then** линейный график скидка↔рейтинг.
3. **Given** графики, **When** ужесточение фильтра, **Then** обе диаграммы пересчитаны.

---

### User Story 4 - Scheduled parsing (FE-01, Priority: P2)

Пользователь настраивает автосбор по сохранённому запросу по расписанию (напр.
каждые 6 часов); система запускает сбор без ручного участия и пополняет историю.

**Why this priority**: превращает разовый снимок в мониторинг; предпосылка истории цен.

**Independent Test**: создать расписание с коротким интервалом → по срабатыванию
появляется новый успешный ParseRun и обновлённые данные; расписание можно
включить/выключить/удалить.

**Acceptance Scenarios**:

1. **Given** сохранённый запрос, **When** создано расписание «каждые 6 ч», **Then** сбор запускается автоматически по интервалу.
2. **Given** активное расписание, **When** пользователь его отключает, **Then** новые автозапуски прекращаются.
3. **Given** автозапуск упал (WB недоступен), **When** следующий тик, **Then** система повторяет по расписанию, прошлые данные целы.

---

### User Story 5 - Asynchronous collection (FE-02, Priority: P2)

Сбор больших выборок не блокирует запрос: `POST /api/parse/` ставит задачу в
очередь и возвращает идентификатор; статус (`pending/running/done/failed`) можно
опросить; UI показывает прогресс.

**Why this priority**: без async расписание и большие категории упираются в таймауты.

**Independent Test**: `POST /api/parse/` → 202 + `task_id`; опрос статуса переходит в
`done` с итоговыми счётчиками; при сбое → `failed` с причиной.

**Acceptance Scenarios**:

1. **Given** запрос, **When** `POST /api/parse/`, **Then** ответ 202 с `task_id`, HTTP не ждёт завершения.
2. **Given** запущенная задача, **When** опрос `GET /api/tasks/{id}/`, **Then** статус и счётчики (created/updated).
3. **Given** задача в очереди, **When** идентичный повторный запуск, **Then** задача идемпотентна (нет двойного сбора того же запроса в один момент).

---

### User Story 6 - Parser anti-bot resilience (FE-03, Priority: P2)

Парсер устойчив к ограничениям WB: ротация User-Agent и (опционально) прокси,
экспоненциальный backoff, ретраи, тайм-ауты; временные сбои не приводят к потере
уже собранного.

**Why this priority**: без этого автосбор по расписанию быстро упрётся в блокировки.

**Independent Test**: при смоделированных 429/таймаутах адаптер повторяет с backoff и
в итоге собирает данные либо возвращает управляемую ошибку `UpstreamUnavailable`.

**Acceptance Scenarios**:

1. **Given** WB отвечает 429, **When** сбор, **Then** адаптер выжидает (backoff) и повторяет до предела попыток.
2. **Given** исчерпаны попытки, **When** сбор, **Then** возвращается `UpstreamUnavailable`, частичных битых записей нет.
3. **Given** настроен список прокси/UA, **When** сбор, **Then** запросы чередуют UA/прокси.

---

### User Story 7 - Price history (FE-04, Priority: P2)

Каждый сбор фиксирует снимок цены/скидки/рейтинга товара во времени; пользователь
видит динамику по товару и по запросу.

**Why this priority**: ключевой аналитический скачок; опирается на US1 (+US4 для регулярности).

**Independent Test**: два сбора с разными ценами → история товара содержит две точки;
`GET /api/products/{wb_id}/history/` возвращает временной ряд.

**Acceptance Scenarios**:

1. **Given** товар собран дважды с разной ценой, **When** запрос истории, **Then** ≥2 точки в хронологическом порядке.
2. **Given** история есть, **When** просмотр товара, **Then** график динамики цены/скидки.
3. **Given** снимки старше срока хранения, **When** политика ретенции, **Then** старые точки прореживаются/удаляются согласно настройке.

---

### User Story 8 - Extended analytics (FE-05, Priority: P2)

Агрегаты по текущей выборке/запросу: средняя/медианная цена, разброс, доля товаров
со скидкой, средняя скидка, топ по отзывам, распределения — считаются на стороне
БД и отдаются через `GET /api/stats/`.

**Why this priority**: снимает ограничение «тянуть всё на клиент», даёт продуктовую аналитику.

**Independent Test**: на известной выборке `GET /api/stats/?query=...` возвращает
корректные средние/медиану/долю скидок, согласованные с данными.

**Acceptance Scenarios**:

1. **Given** выборка, **When** `GET /api/stats/`, **Then** средняя/медианная цена, средняя скидка, доля со скидкой.
2. **Given** фильтры, **When** запрос статистики с теми же фильтрами, **Then** агрегаты по той же подвыборке, что и таблица.
3. **Given** пустая выборка, **When** запрос, **Then** нулевые/пустые агрегаты без ошибки.

---

### User Story 9 - Query / category comparison (FE-06, Priority: P3)

Пользователь сравнивает два и более запроса/категории бок о бок: цены, средние
скидки, конкуренция (число товаров, распределения).

**Why this priority**: ценно, но надстройка над аналитикой (US8).

**Independent Test**: выбрать 2 запроса → таблица/графики сравнения показывают
метрики каждого рядом.

**Acceptance Scenarios**:

1. **Given** собраны два запроса, **When** сравнение, **Then** метрики обоих отображаются рядом.
2. **Given** сравнение, **When** смена набора запросов, **Then** представление пересчитывается.

---

### User Story 10 - Price alerts & notifications (FE-07, Priority: P3)

Пользователь заводит правило («цена товара X ниже N» или «средняя цена по запросу
просела на ≥15%»); при срабатывании после сбора приходит уведомление (email/Telegram).

**Why this priority**: удержание и проактивная ценность; опирается на историю (US7) и auth (US12).

**Independent Test**: правило + сбор, дающий срабатывание → фиксируется событие
алерта и уходит уведомление (через фейковый нотификатор в тестах).

**Acceptance Scenarios**:

1. **Given** правило «< N», **When** сбор фиксирует цену ниже N, **Then** создаётся событие алерта и отправляется уведомление.
2. **Given** правило, **When** порог не пройден, **Then** уведомления нет.
3. **Given** сработавший алерт, **When** повтор той же цены, **Then** нет спама (дедуп/кулдаун уведомлений).

---

### User Story 11 - Data export (FE-08, Priority: P3)

Текущую (отфильтрованную) выборку можно выгрузить в CSV/Excel.

**Why this priority**: полезно для оффлайн-анализа; тонкая надстройка над read-моделью.

**Independent Test**: `GET /api/export/?format=csv&...filters` возвращает файл, чьи
строки соответствуют тем же фильтрам, что и таблица.

**Acceptance Scenarios**:

1. **Given** фильтры, **When** экспорт CSV, **Then** файл содержит ровно отфильтрованные строки с колонками таблицы.
2. **Given** большой набор, **When** экспорт, **Then** выгрузка потоковая, без падения по памяти.

---

### User Story 12 - Auth & saved searches (FE-09, Priority: P2)

Многопользовательский режим: регистрация/вход, свои сохранённые запросы, свои
расписания и алерты, изоляция данных по владельцу.

**Why this priority**: предпосылка персональных расписаний (US4) и алертов (US10).

**Independent Test**: два пользователя → каждый видит только свои сохранённые запросы/
расписания/алерты; неавторизованный доступ к чужим ресурсам запрещён.

**Acceptance Scenarios**:

1. **Given** зарегистрированный пользователь, **When** вход, **Then** доступ к своим сохранённым запросам.
2. **Given** пользователь A создал ресурс, **When** пользователь B запрашивает его, **Then** доступ запрещён (403/404).
3. **Given** публичные каталожные данные, **When** просмотр, **Then** доступны согласно политике (чтение каталога не требует владельца).

---

### Edge Cases

- Пустая выдача WB → сбор завершается с 0 товарами и понятным сообщением.
- WB недоступен/сменил формат → сбор с ошибкой, без частично битых записей; данные целы (US6).
- Пустой результат фильтра → «ничего не найдено», графики/статистика — пустое состояние.
- Некорректные параметры фильтра/статистики → 400, не 500.
- Очень большая выдача → ограничение `max_pages`; async-сбор (US5) для длительных задач.
- Пересечение расписаний / повторный запуск того же запроса → идемпотентность (US5), без двойного сбора.
- Нотификации: недоступен email/Telegram → ретрай с backoff, без потери события алерта.
- Ретенция истории: рост объёма → прореживание/удаление по политике (US7).
- Мультиарендность: пользователь не может читать/менять чужие расписания/алерты/сохранённые запросы (US12).

## Requirements *(mandatory)*

### Functional Requirements — Core

- **FR-001**: Система MUST принимать запрос/категорию и собирать по нему товары с WB.
- **FR-002**: MUST извлекать: название, цену, цену со скидкой, рейтинг, число отзывов.
- **FR-003**: MUST сохранять товары в БД, связывая с запросом.
- **FR-004**: Повторный сбор MUST обновлять запись по идентификатору WB, а не дублировать.
- **FR-005**: Сбой/неполнота одного товара MUST NOT прерывать сбор; логируется.
- **FR-006**: MUST предоставлять `GET /api/products/`.
- **FR-007**: `GET /api/products/` MUST фильтровать по цене (на `sale_price`), рейтингу, числу отзывов.
- **FR-008**: MUST сортировать по цене, цене со скидкой, рейтингу, отзывам, названию (asc/desc).
- **FR-009**: Некорректные параметры MUST давать ошибку валидации, не сбой.
- **FR-010**: Frontend MUST показывать таблицу с 5 колонками.
- **FR-011**: Frontend MUST давать слайдер цен, фильтр мин. рейтинга, фильтр мин. отзывов.
- **FR-012**: Смена фильтра/сортировки MUST обновлять таблицу динамически.
- **FR-013**: Frontend MUST показывать гистограмму распределения цен.
- **FR-014**: Frontend MUST показывать линейный график скидка↔рейтинг.
- **FR-015**: Диаграммы MUST пересчитываться синхронно с фильтрами.
- **FR-016**: MUST давать способ инициировать сбор (UI и скрипт/CLI).

### Functional Requirements — FE-01 Scheduled parsing

- **FR-017**: Система MUST позволять создавать/редактировать/удалять расписание сбора для запроса (интервал/крон).
- **FR-018**: MUST автоматически запускать сбор по расписанию без ручного участия.
- **FR-019**: MUST позволять включать/выключать расписание; отключённое не запускается.

### Functional Requirements — FE-02 Async collection

- **FR-020**: `POST /api/parse/` MUST ставить сбор в очередь и возвращать `task_id` (202), не блокируя запрос.
- **FR-021**: MUST предоставлять статус задачи (`pending/running/done/failed`) с счётчиками и причиной сбоя.
- **FR-022**: Постановка сбора MUST быть идемпотентной для одного запроса в один момент (без дублирующих одновременных задач).

### Functional Requirements — FE-03 Resilience

- **FR-023**: Парсер MUST применять тайм-ауты, ретраи с экспоненциальным backoff к запросам WB.
- **FR-024**: Парсер MUST ротировать User-Agent и (если настроено) прокси.
- **FR-025**: При исчерпании попыток MUST возвращать управляемую ошибку без частичной порчи данных.

### Functional Requirements — FE-04 Price history

- **FR-026**: При каждом сборе система MUST фиксировать снимок (цена, цена со скидкой, рейтинг, время) для товара.
- **FR-027**: MUST предоставлять историю по товару (`GET /api/products/{wb_id}/history/`).
- **FR-028**: MUST применять настраиваемую политику ретенции снимков.

### Functional Requirements — FE-05 Extended analytics

- **FR-029**: MUST предоставлять `GET /api/stats/` с агрегатами (средняя/медианная цена, средняя скидка, доля со скидкой, топ по отзывам).
- **FR-030**: Агрегаты MUST учитывать те же фильтры, что и таблица.
- **FR-031**: Агрегаты MUST считаться на стороне БД (без выгрузки всех строк на клиент).

### Functional Requirements — FE-06 Comparison

- **FR-032**: MUST позволять сравнивать метрики двух и более запросов/категорий.
- **FR-033**: Сравнение MUST обновляться при изменении набора запросов.

### Functional Requirements — FE-07 Alerts

- **FR-034**: Пользователь MUST мочь создать правило алерта (порог по цене товара или по средней цене запроса).
- **FR-035**: После сбора система MUST вычислять срабатывания и создавать событие алерта.
- **FR-036**: MUST отправлять уведомление (email/Telegram) при срабатывании.
- **FR-037**: MUST предотвращать спам (дедуп/кулдаун) и ретраить доставку при сбое канала.

### Functional Requirements — FE-08 Export

- **FR-038**: MUST экспортировать текущую отфильтрованную выборку в CSV и Excel.
- **FR-039**: Экспорт MUST быть потоковым и соответствовать активным фильтрам.

### Functional Requirements — FE-09 Auth & saved searches

- **FR-040**: MUST поддерживать регистрацию и аутентификацию пользователей.
- **FR-041**: Пользователь MUST мочь сохранять/удалять свои запросы.
- **FR-042**: Расписания и алерты MUST принадлежать пользователю и быть изолированы по владельцу.
- **FR-043**: Доступ к чужим пользовательским ресурсам MUST запрещаться (403/404).
- **FR-044**: Чтение публичного каталога товаров MUST быть доступно согласно политике доступа.

### Key Entities *(include if feature involves data)*

- **Product (Товар)**: идентификатор WB (уникальный), название, цена, цена со скидкой, рейтинг, число отзывов, запрос-источник, отметки времени.
- **SearchQuery (Запрос сбора / Parse Run)**: строка/категория запроса и метаданные запуска; связь один-ко-многим с товарами. (Единый термин во всех артефактах.)
- **PriceSnapshot (Снимок)**: точка истории для товара (цена, цена со скидкой, рейтинг, timestamp). Append-only.
- **Schedule (Расписание)**: привязка запроса к интервалу/крону, флаг активности, владелец.
- **ParseJob / Task (Задача сбора)**: async-задача сбора со статусом, счётчиками, причиной сбоя.
- **User (Пользователь)**: учётная запись; владелец сохранённых запросов, расписаний, алертов.
- **SavedSearch (Сохранённый запрос)**: пользовательский именованный запрос + фильтры.
- **AlertRule (Правило алерта)**: условие (порог) над товаром/запросом, владелец, канал.
- **AlertEvent (Событие алерта)**: факт срабатывания правила с меткой времени (для дедупа/истории).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: По валидному запросу собирается ≥100 товаров (при наличии) с 5 полями за запуск.
- **SC-002**: Смена фильтра обновляет таблицу и обе диаграммы < 1 c при выборке до 1000 товаров.
- **SC-003**: 100% комбинаций фильтров/сортировки согласованы между таблицей, графиками и статистикой.
- **SC-004**: Повтор сбора не увеличивает число уникальных товаров (0 дублей по WB id).
- **SC-005**: Некорректный ввод в 100% случаев даёт понятную ошибку, не 500.
- **SC-006**: Расписание срабатывает в пределах ±1 интервала планировщика; отключённое не запускается (0 автозапусков).
- **SC-007**: `POST /api/parse/` возвращает ответ < 500 мс независимо от размера сбора (сбор идёт в фоне).
- **SC-008**: При смоделированных 429/таймаутах сбор завершается успешно или управляемой ошибкой в 100% случаев (без 500/битых записей).
- **SC-009**: После N сборов история товара содержит N точек (при изменяющихся данных), доступных через API.
- **SC-010**: `GET /api/stats/` для выборки до 100k строк отвечает < 1 c (агрегация в БД).
- **SC-011**: Сработавший алерт доставляет ≤1 уведомление за кулдаун (0 дублей уведомлений при неизменной цене).
- **SC-012**: Пользователь никогда не получает доступ к чужим сохранённым запросам/расписаниям/алертам (0 утечек в тестах мультиарендности).

## Delivery Phasing

Все функции — в объёме, но поставляются инкрементально (порядок для реализации):

- **Phase A — Core MVP**: US1, US2, US3 (собрать → фильтровать/сортировать → графики).
- **Phase B — Monitoring & Analytics**: US6 (resilience), US5 (async), US4 (schedule), US7 (history), US8 (stats), US12 (auth/saved).
- **Phase C — Engagement & Reach**: US9 (comparison), US10 (alerts), US11 (export).

Каждая история независимо тестируема; Phase A остаётся демонстрируемым MVP.

## Assumptions

- Источник — публичная JSON-выдача WB (без авторизации); формат волатилен, парсер изолирован и покрыт тестами на фикстурах.
- «Цена» — базовая, «цена со скидкой» — итоговая; обе нормализуются в рубли; фильтры цены — по цене со скидкой.
- «Размер скидки» = цена − цена со скидкой (рубли, абсолютно); процент — вторично.
- Ценовые диапазоны гистограммы — равной ширины по диапазону выборки.
- Async/расписание/алерты используют брокер (Redis) и воркеры; в тестах — синхронный/фейковый режим.
- Ретенция истории настраивается (по умолчанию — разумный срок), не безгранична.
- Уведомления — email и Telegram; учётные данные каналов — из окружения.
- Аутентификация — сессии/JWT (DRF); чтение каталога может быть публичным, пользовательские ресурсы — приватные.
